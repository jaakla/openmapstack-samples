# PV location analysis

An interactive planning prototype for [issue #4](https://github.com/jaakla/openmapstack-samples/issues/4): draw a hypothetical PV polygon, change its orientation, tilt, mounting height and installed capacity, then compare clear-sky, weather-adjusted and locally shaded production. Estimate local day/night consumption or privately import a compatible Enefit consumption CSV to separate on-site PV use, grid imports and surplus sales. Export a PDF of the current scenario, including its map, energy balance, value estimates and evidence.

Select another location in Estonia to load its own bounded terrain, imagery, building and historical weather context. The retained Tartu scenario remains the reproducible baseline; live selections are exploratory and show their own request provenance. Optional battery storage compares historical dispatch with the same scenario without storage, including conversion losses and explicit operating limits.

The bounded pilot covers a 2 × 2 km area around Tartu, Estonia (58.37°N, 26.72°E). The initial 30 × 12 m, 20 kWp polygon is an explicitly hypothetical planning scenario, not an observed installation or a site recommendation. Weather is an ERA5 grid estimate, and local obstruction geometry comes from official Maa- ja Ruumiamet DSM/DTM data. Buildings provide map context; the DSM supplies obstruction heights, including vegetation.

## Run the app

Requirements: Node.js 24 or newer and npm. The committed browser data are sufficient for local use; no API credentials or online source refresh are required.

```sh
cd pv-location
npm ci
npm run dev -- --host 127.0.0.1
```

Open the URL printed by Vite. A production build is produced by `npm run build`; `npm run preview` serves it. Map tiles require internet access. All browser scenario changes are exploratory; the reset control returns to the canonical scenario. An exported scenario is a draft until adopted into the pipeline inputs and rerun.

The published consumption baseline is **10 kWh during 07:00–23:00 and 4 kWh during the local night**, using `Europe/Tallinn`. These are editable assumptions, not measured demand. The default import-price adder is **0 EUR/MWh**: avoided purchases are valued at spot prices only, with no invented VAT or grid tariff. Surplus exports use actual historical EE spot prices minus the sales margin.

Consumption uploads stay in browser memory. CSV interpretation and coverage are shown before results are used; missing demand remains unknown unless estimate filling is explicitly enabled. A user-initiated scenario JSON export may include the normalized profile for reimport and is therefore a private file. PDFs contain the modeled aggregates and source label, not the household's interval rows or account identifiers. Nothing uploads the consumption profile to a server or writes it into this repository.

The PDF button reports the current exploratory or published scenario. A separate [canonical report](public/data/canonical-report.pdf) is generated by the pipeline from the pinned baseline; its map crops the retained official aerial image around the hypothetical polygon, with the footprint overlaid.

Storage is off in the published baseline. When enabled, its initial automatic capacity is twice PV kWp in kWh, with editable charge/discharge power or current, efficiency, reserve, grid charging, battery export and cycling cost. This is an explicit sizing assumption. Dispatch uses historical price knowledge and a finite optimization resolution; it is not a live trading forecast or a battery investment recommendation. Storage adds a fourth PDF page with the comparison and settings.

Run the engine and browser checks with:

```sh
npm test
npx playwright install chromium
npm run test:browser
```

To use an existing Chromium binary, set `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` to its absolute executable path. The browser suite starts its configured local server and exercises scenario controls, drawing, reset, exports, invalid measurement input and responsive layouts. The OpenMapStack verification below additionally checks the generated direct-file dashboard and its canonical evidence.

Independent PDF parsing checks use Python `pypdf==6.20.1`; those checks are explicitly skipped if it is absent. CI installs the pinned parser. For the full local suite, install it into the Python environment described below with `uv pip install --python .venv/bin/python pypdf==6.20.1`, then run `PATH="$PWD/.venv/bin:$PATH" npm test`.

## Reproduce the analysis

The analysis uses the latest GitHub `main` of [OpenMapStack skills](https://github.com/jaakla/openmapstack-skills) checked out for this implementation: commit `a3df1cb8126d5222fbb27e3f1dba49aca01b6302` (toolkit 0.4.0). That commit is pinned so a future `main` change cannot silently change this result.

With [uv](https://docs.astral.sh/uv/) installed:

```sh
cd pv-location
uv venv .venv --python 3.12
uv pip install --python .venv/bin/python -r requirements.txt
.venv/bin/playwright install chromium
.venv/bin/openmapstack validate project.yaml --preflight
.venv/bin/openmapstack run project.yaml
.venv/bin/openmapstack verify project.yaml --rerun
```

The canonical `pipeline.py` checks immutable source hashes, applies the declared planning scenario, consumption and storage assumptions, invokes the same JavaScript engines used by the app, writes analytical CSV/GeoJSON outputs and browser data, generates the canonical PDF with the shared report builder, builds the app, embeds provenance and OpenMapStack delivery evidence, and writes findings, validation and a run inventory. A clean rerun copies only declared inputs and dependencies into an empty workspace and rebuilds the selected dashboard. The canonical pipeline installs npm dependencies with `npm ci` when absent. Python dependencies are installed by the CLI from the pinned runtime declaration; `requirements.txt` also provides a manual installation path.

The generated `dist/index.html` embeds the application, workers, source data and aerial context so it can also be opened directly from disk. The normal Vite server remains convenient during development. The toolkit's dashboard checks use this direct-file view.

After intentionally editing an input or analytical implementation, run `.venv/bin/python pipeline.py` once before `openmapstack run`. This regenerates the truthful run inventory: the pinned toolkit's CLI preflight otherwise rejects files that differ from the previous inventory before executing the requested rerun. Never edit the inventory hashes by hand.

Source acquisition is a separate, explicit refresh: `python acquire.py --refresh` downloads mutable upstream services and replaces immutable snapshots. `python acquire.py` verifies retained artifacts offline; `python acquire.py --normalize` rebuilds normalized inputs from the raw snapshots (requires NumPy and GDAL bindings). Review the source lock and update `project.yaml` pins before accepting refreshed bytes. Ordinary runs make no weather, market, WFS or WCS requests. The selected delivery is the custom web dashboard; QGIS and Observable are not selected.

Selecting a new browser AOI does make source requests. Its responses are separate from the pinned baseline and require network access. A failed or incomplete request is not replaced with Tartu data. To adopt another area as the public canonical project, retain its source responses and update the source lock, AOI, override and manifest before rerunning verification.

## Evidence and limits

- [Findings](findings.md) contains pipeline-derived results and links to the exact analytical outputs.
- [Project manifest](project.yaml) records source pins, assumptions, thresholds, output definitions and runtime dependencies.
- [Methodology](docs/methodology.md) explains temporal conventions, local shadows and the revenue calculation.
- [Estonia area selection](docs/area-selection.md) records live source requests, coverage checks and reusable area bundles.
- [Storage model](docs/storage.md) defines dispatch, conversion losses, economic comparisons and limitations.
- [Canonical PDF](public/data/canonical-report.pdf) presents the baseline scenario, consumption balance, economics and evidence.
- [Validation report](validation/latest-report.json) and [run records](runs/) preserve executed checks and hashes.

The app supports comparison with the owner's measured production CSV, but no owner's production record was supplied. The retained validation reports that comparison as `not_testable`; it does not claim field accuracy. Automated PV detection from aerial imagery is the issue's later phase and is not trained or evaluated here. Government solar records available to this pilot are aggregate municipality statistics and cannot validate individual installations. The app estimates energy and scenario value; it does not establish grid connection, engineering feasibility, consent, capital cost or an actual retail bill. Curtailment and financing are not modeled, and storage is a historical operating scenario rather than an investment forecast.

Issue coverage: manual polygon and equipment parameters, DSM-based local shadows, the three energy comparisons, shadow energy/value loss, actual 2024/2025 prices and a production-CSV comparison interface are implemented. Extensions add day/night estimates, private Enefit CSV import, self-consumption/import/export accounting, current-scenario PDF reports, bounded Estonia AOI loading and optional battery dispatch. Owner-data accuracy validation and the later imagery-detection extension remain unavailable and explicitly unvalidated.
